# Local LLM Werewolf
## 基于 Ollama 的单机、多人格、对话式狼人杀游戏设计文档

**项目类型：** 单机模拟多人社交推理游戏  
**核心技术：** HTML5、CSS、JavaScript、Ollama、本地轻量 API 服务  
**游戏模式：** 单人参与 + 多个 LLM Bot  
**核心特色：** Personality 驱动的行为、可观察的非语言动作、跨局记忆、自主推理与社交互动  
**设计目标：** 让玩家感觉自己面对的不是一群预设台词的 NPC，而是一群具有不同性格、独立记忆、各自判断和社交策略的真实玩家。

---

# 一、游戏概念与核心设计理念

## 1.1 游戏简介

这是一个模拟多人狼人杀的单机游戏。

玩家进入游戏后，可以选择自己想要参与的游戏人数，为各个 Bot 分配不同的 Personality。系统随机生成角色身份，开始一场由本地大语言模型驱动的狼人杀。

每个 Bot 都拥有自己的：

- Personality：定义性格、说话方式、行为习惯与社交策略。
- Memory：记录对其他玩家的了解、怀疑、信任、投票历史以及过去游戏的经历。
- Hidden Role：当前游戏中的真实身份和该身份允许知道的信息。
- Decision Process：根据游戏规则、性格、记忆和当前局势决定下一步行动。
- Public Behavior：其他玩家能够观察到的语言、表情、动作、提问和投票行为。

白天，Bot 们轮流自由活动。它们可以主动搭话、质疑某个玩家、回答问题、表现出紧张或自信、观察其他玩家，甚至根据自己的性格选择沉默。

玩家可以随时观察某个 Bot 的公开行为，也可以直接向它提问。Bot 不一定会配合玩家，也可能撒谎、回避问题、误判局势，或者因为此前的互动而改变对玩家的看法。

夜晚，各个拥有夜间行动能力的角色根据各自的记忆、身份和策略做出决定。狼人独立选择猎杀目标，预言家查验玩家，医生执行救援。

Game Master 负责游戏规则、阶段控制、结果判定与公开信息，确保 LLM 的自由行为不会破坏游戏运行。

## 1.2 五项核心设计原则

### 原则 A：LLM 决定行为，游戏引擎决定事实

Bot 的性格、推理和社交决策由本地 LLM 生成，但游戏规则必须由确定性的游戏引擎执行。

例如：

- Bot 可以怀疑一个无辜玩家，但不能把这个怀疑直接变成该玩家的真实身份。
- Bot 可以声称自己是预言家，但引擎不能因此把它的真实身份改成预言家。
- Bot 可以想攻击已经死亡的玩家，但游戏引擎必须拒绝非法目标。
- Bot 可以声称自己昨晚查验了某人，但只有真正执行过查验的玩家才拥有相应的私有查验结果。

这条原则贯穿整个系统。

### 原则 B：每个 Bot 都是独立的游戏参与者

每个 Bot 必须拥有独立的 Personality、Memory 和当前局势判断。

即使两个 Bot 使用同一个 Ollama 模型，它们也不能共享未经授权的私人记忆、推理上下文或身份信息。

### 原则 C：人格必须影响决策，而不只是说话风格

一个话少、谨慎、证据导向的 Bot，应该更少主动发言，更倾向于观察和积累证据。

一个自信、喜欢领导讨论的 Bot，可能频繁提问、总结局势并推动其他玩家站队。

一个多疑、冲动的 Bot，可能过早锁定嫌疑人，并在被反驳后产生明显的情绪反应。

Personality 不能只是为所有 Bot 的同一份结论换一种措辞，而应该影响它们选择什么行为，以及何时采取行为。

### 原则 D：记忆必须具有连续性，但不能破坏新的游戏身份

Bot 应该记得过去几局中玩家的行为、自己的误判、曾经的合作关系以及其他 Bot 的社交习惯。

但是，上一局的狼人身份不能直接成为下一局的狼人证据。

系统必须区分：

1. 当前游戏中的事实与秘密。
2. 当前游戏中的怀疑和临时判断。
3. 跨局积累的社交印象与历史经历。

### 原则 E：上下文有限时，优先保留对当前决策真正有用的信息

不能将整个游戏的全部聊天记录、完整 Personality 文件和所有历史 Memory 一股脑地塞进每次 Prompt。

系统应该根据 Bot 当前要做的事情，选择最相关的信息，并对过长的记忆进行压缩。

# 二、总体游戏架构

## 2.1 系统组成

整个游戏由五个主要模块组成。

### 1. HTML5 Game Client

负责玩家可见的交互界面，包括：

- 游戏大厅。
- Personality 管理器。
- 游戏人数和角色配置。
- 对话记录面板。
- Bot 行为观察界面。
- 玩家提问界面。
- 白天与黑夜阶段控制。
- 游戏状态与公开结果。
- 可选的开发调试面板。

前端只负责显示公开信息和收集玩家操作，不负责决定真实身份、狼人胜负或其他隐藏状态。

### 2. Game Engine

游戏引擎是整个系统的权威状态管理者。

它负责：

- 随机分配角色。
- 管理所有参与者的生死状态。
- 控制白天和黑夜。
- 维护合法行动列表。
- 判断胜负。
- 处理狼人投票和特殊角色行动。
- 统计对话数量。
- 验证 LLM 返回的行动是否合法。
- 生成 Game Master 的规则公告。

游戏引擎应尽量采用普通 JavaScript 逻辑实现，避免依赖 LLM 做精确判断。

### 3. Bot Agent Manager

每个 Bot 都是一个独立的 Agent 实例。

主要职责：

- 加载指定 Personality。
- 获取该 Bot 有权知道的游戏信息。
- 读取自身记忆。
- 组装 Prompt。
- 调用 Ollama。
- 解析 LLM 返回的行动。
- 验证行动并交给 Game Engine。
- 将最终发生的事件写入 Bot Memory。

Bot Agent 不应直接修改游戏的核心状态，只能提出行动请求。

### 4. Memory Manager

集中负责所有 Bot 的记忆读写与压缩。

每个 Bot 拥有单独的记忆对象，但可以由统一的 Memory Manager 管理。

Memory Manager 负责：

- 记录当前局信息。
- 更新对其他玩家的看法。
- 记录已确认事实与尚未证实的猜测。
- 压缩较旧的事件。
- 在新游戏开始时归档上一局。
- 保留跨局社交记忆。
- 控制注入 Prompt 的记忆长度。

### 5. Ollama Adapter

负责与本机 Ollama 通信。

每次调用都应包含明确的模型名称、系统指令、上下文配置、生成参数和响应格式要求。

同一个本地模型可以供多个 Bot 共用。各 Bot 的差异主要来自自己的 Personality、Memory 与当前局势，而不是必须使用不同模型。

## 2.2 推荐技术架构

```text
┌─────────────────────────────────┐
│          HTML5 Frontend         │
│                                 │
│  Lobby / Dialogue / Observation │
│  Personality Editor / Game Log  │
└────────────────┬────────────────┘
                 │ Local HTTP API
┌────────────────▼────────────────┐
│        Local Game Backend       │
│                                 │
│  Game Engine                    │
│  Bot Agent Manager              │
│  Memory Manager                 │
│  Personality File Manager       │
│  Prompt Builder                 │
│  Ollama Adapter                 │
└────────┬────────────────┬───────┘
         │                │
┌────────▼───────┐ ┌──────▼────────┐
│ Personality    │ │ Ollama        │
│ JSON Files     │ │ Local Models  │
└────────────────┘ └───────────────┘
```

### 一个重要的技术限制

浏览器加载普通静态 HTML 页面后，不能像 Node.js 程序那样任意读写服务器磁盘文件。

因此，建议采用：

- 静态内容服务器提供 HTML、CSS 和 JavaScript。
- 一个轻量级本地 API 服务负责 Personality 文件的创建、读取、修改和删除，以及游戏状态管理。
- 本地 API 服务通过 HTTP 调用 Ollama。

两者可以运行在同一台电脑上。

这样依然是单机游戏，前端仍然是静态网页，而且能够真正实现文件管理、独立 Bot 记忆和跨局状态。

建议使用 Node.js 实现本地 API 服务，因为前后端都可以使用 JavaScript。也可以使用其他本地后端语言。

## 2.3 两种不同的储存机制

本项目应明确区分以下两类数据。

**Personality 文件**

保存在本地磁盘中，方便长期管理、修改、导入和导出。

**Bot Memory**

默认保存在本地游戏后端的 RAM 中，不自动写入磁盘。

只要游戏后端仍在运行，Memory 就可以跨越连续多局游戏。游戏进程退出后，Memory 全部消失。

这种设计符合“记忆在内存中、可以跨局、不永久保存”的要求。

# 三、游戏参与者与角色系统

## 3.1 参与者模型

所有参与者，包括玩家和 Bot，都应采用统一的 Participant 数据结构。

每个参与者拥有：

- `participantId`：稳定的参与者 ID。
- `displayName`：游戏中的名字。
- `participantType`：`human` 或 `bot`。
- `personalityId`：对应的 Personality ID，玩家可为空。
- `role`：本局真实身份。
- `alive`：是否存活。
- `publicStatus`：公开可见状态。
- `privateState`：只有本人或引擎可以访问的秘密状态。

Bot 的 `participantId` 应保持稳定，不能每次说话都临时创建新的参与者。

跨局 Memory 最好绑定到稳定的 Agent 身份，而不是单纯绑定某一场游戏里的座位编号。

## 3.2 游戏角色

建议将角色拆分为基础角色和扩展角色。

### 狼人 Werewolf

狼人每晚参与猎杀投票。

狼人的私有知识包括：

- 自己的真实身份。
- 其他存活狼人的真实身份。
- 自己的推理和历史记录。

狼人不知道其他非狼人参与者的真实身份。

狼人可以白天伪装成任何角色，可以撒谎、引导讨论，或试图让其他玩家相互怀疑。

不同狼人可以拥有完全不同的策略。例如，一个狼人偏向保守隐藏，另一个狼人偏向领导讨论，甚至两者可能因为战术分歧而产生争论。

### 村民 Villager

村民没有夜间特殊技能。

他们的任务是通过观察、提问、分析发言和投票找出狼人。

村民不应该自动知道任何其他人的身份。其怀疑必须来自公开事件、自己的判断或者 Personality 所产生的决策偏好。

### 预言家 Seer

预言家每晚可以查验一名合法目标的阵营。

查验结果以私有信息的方式发送给预言家。

如果某位 Bot 是预言家，只有它可以收到真实查验结果。其他 Bot 不得读取该结果，除非预言家通过公开发言告诉它们。

预言家可以选择公开身份，也可以隐藏身份，具体取决于其 Personality 和策略。

### 医生 Doctor

医生每晚可以选择一名合法的救援目标。

基础规则建议：

- 每晚最多进行一次救援。
- 自救规则通过配置决定。
- 被救援的目标如果受到当晚的猎杀攻击，则不会因该攻击死亡。

医生只能根据自己已知的信息作出决策，不能直接读取狼人投票结果。

### 扩展角色

后续可以加入：

- Hunter：死亡时可发动一次反击。
- Witch：拥有有限次数的救援或毒杀能力。
- Guard：保护一名玩家免受夜间攻击。
- 更多可由配置定义的特殊角色。

第一版不建议同时加入过多特殊角色。先保证基础狼人、村民、预言家和医生能够完整运行。

## 3.3 人数与角色配比

人数应以**所有参与者总数**计算，包括人类玩家。

可以提供推荐的角色预设。例如：

| 总人数 | 狼人 | 预言家 | 医生 | 村民 |
|---:|---:|---:|---:|---:|
| 5 | 1 | 1 | 1 | 2 |
| 6 | 2 | 1 | 1 | 2 |
| 7 | 2 | 1 | 1 | 3 |
| 8 | 2 | 1 | 1 | 4 |
| 9 | 2 | 1 | 1 | 5 |
| 10 | 3 | 1 | 1 | 5 |

以上是简化游戏的默认预设，可以在后续增加猎人、女巫等角色。

游戏开始前，引擎必须验证：

- 所有角色数量之和等于参与者总人数。
- 狼人数量大于零。
- 所有特殊角色的数量合法。
- 游戏规模不会造成明显不合理的阵营平衡。

如果某个预设不满足这些条件，应阻止游戏开始并给出明确提示。

## 3.4 游戏开始时的角色介绍

Game Master 在游戏开始时简要宣布本局包含的角色类型和数量，并解释基础规则。

例如：

> 欢迎来到本局狼人杀。
>
> 本局共有 7 位玩家，包括 2 名狼人、1 名预言家、1 名医生和 3 名村民。
>
> 白天是自由讨论时间。你可以观察其他玩家的公开行为，也可以主动向任何存活的玩家提问。
>
> 黑夜降临后，狼人将选择猎杀目标，预言家进行查验，医生执行救援。
>
> 请记住：发言不等于事实，怀疑不等于证据。最终结果以游戏规则和真实身份为准。
>
> 你的身份已私下分配。游戏现在开始。

这段公告只公布角色数量，不公布谁获得了什么身份。

玩家自身的身份应通过私人界面显示。Bot 的真实身份对玩家保密，除非游戏规则明确宣布某人身份。

# 四、Personality 系统设计

## 4.1 Personality 的作用

Personality 是 Bot 的核心行为配置。

它不是游戏角色，也不直接决定 Bot 属于哪个阵营。相同的 Personality 可以在不同局里成为狼人、村民、预言家或医生。

Personality 主要影响：

- 是否主动发言。
- 喜欢怎样提问。
- 如何表达怀疑。
- 如何处理被质疑的情况。
- 是否喜欢观察细节。
- 是否倾向于信任他人。
- 是否善于欺骗或伪装。
- 会表现出哪些小动作。
- 如何与不同性格的参与者建立关系。

Personality 应由一组结构化参数和自然语言描述共同组成。

## 4.2 Personality 文件结构

建议使用 JSON 格式，方便验证、编辑与版本管理。

示例：

```json
{
  "id": "calm_observer",
  "name": "冷静的观察者",
  "version": 1,
  "description": "冷静、谨慎，善于观察细节，习惯在证据不足时保持沉默。",
  "speakingStyle": {
    "verbosity": 25,
    "directness": 35,
    "formality": 55,
    "emotionality": 20,
    "questionFrequency": 30
  },
  "socialStyle": {
    "sociability": 25,
    "trustingness": 30,
    "conflictAvoidance": 60,
    "leadership": 20
  },
  "strategyStyle": {
    "riskTolerance": 30,
    "evidenceFocus": 90,
    "suspicionThreshold": 75,
    "deceptionSkill": 25,
    "adaptability": 65
  },
  "behavior": {
    "gestureFrequency": 35,
    "signatureGestures": [
      "发言前短暂沉默",
      "轻轻敲两下桌面",
      "被质疑时微微皱眉"
    ],
    "gesturesWhenNervous": [
      "短暂移开视线"
    ],
    "gesturesWhenConfident": [
      "平静地直视对方"
    ]
  },
  "speechHabits": [
    "习惯先确认事实，再表达判断",
    "偶尔使用简短的反问句",
    "不喜欢无证据的强烈指控"
  ],
  "socialTactics": [
    "喜欢询问发言前后的逻辑是否一致",
    "倾向于保留暂时无法证实的判断"
  ],
  "avoidances": [
    "不要每次发言都重复相同句式",
    "不要无缘无故使用夸张的情绪表达"
  ]
}
```

## 4.3 Personality 参数的含义

数值建议统一使用 0～100 的范围。

| 参数 | 含义 |
|---|---|
| verbosity | 发言时倾向于长篇解释还是简短回答 |
| directness | 直接指出问题的程度 |
| formality | 语言正式程度 |
| emotionality | 公开表达情绪的程度 |
| questionFrequency | 主动提问的倾向 |
| sociability | 主动接近其他玩家的倾向 |
| trustingness | 默认给予他人信任的程度 |
| conflictAvoidance | 回避正面冲突的程度 |
| leadership | 主动组织讨论和影响他人的倾向 |
| riskTolerance | 愿意承担公开指控风险的程度 |
| evidenceFocus | 重视客观事实和前后矛盾的程度 |
| suspicionThreshold | 产生明确怀疑前需要的证据强度 |
| deceptionSkill | 在身份不利时倾向采用伪装和误导策略的程度 |
| adaptability | 根据新证据改变判断的倾向 |
| gestureFrequency | 做出非语言动作的频率 |

这些参数不是直接的数学胜率修正，而是影响 LLM 行为的指引。

例如，`evidenceFocus = 90` 不意味着 Bot 必须判断正确，而是意味着其做决定时更重视证据和逻辑。

`deceptionSkill = 90` 也不意味着 Bot 一定说谎，而是意味着当其角色目标需要伪装时，更倾向于设计有连贯性的策略。

## 4.4 Personality 文件管理界面

界面至少应支持以下功能。

**创建**

用户输入名称、描述以及相关参数，保存为新 Personality 文件。

**编辑**

可以使用表单编辑，也可以提供高级 JSON 编辑模式。

**复制**

复制现有 Personality 并修改局部特征，快速产生具有相似基础但不同风格的 Bot。

**删除**

删除前提示确认，并检查当前是否有游戏正在引用该 Personality。

删除 Personality 文件不应自动删除对应 Agent 已经积累的 Memory。

**预览**

显示该人格在不同情境下可能采取的行为，例如：

- 遇到陌生玩家时如何搭话。
- 发现逻辑矛盾时如何发问。
- 被直接质疑时如何回应。
- 怀疑某人但证据不足时怎么做。
- 感到紧张时有哪些公开动作。

预览只能演示人格倾向，不应将示例台词固定为每局必须出现的内容。

## 4.5 Personality 文件与 Agent 身份的关联

建议将稳定的 Bot Agent 身份绑定到 `personalityId`。

玩家选择新一局的 Bot 阵容时，可以选择：

- 保留上一局的 Bot 组合。
- 重新抽取 Personality。
- 手动分配每个 Bot 的 Personality。
- 允许或禁止同一个 Personality 重复使用。

默认应尽量避免两个 Bot 使用相同 Personality。

如果 Personality 文件在游戏中被编辑，已经开始的本局建议继续使用开局时加载的 Personality 快照，以避免一场游戏进行中人格规则突然变化。

下一局再应用新的版本。

# 五、Bot Memory 记忆系统

这是本项目最重要的系统之一。

如果 Memory 设计不好，Bot 会忘记刚才发生的事情，重复提出相同的问题，或者在下一局忘记曾经与某个玩家的互动。

另一方面，如果把所有信息无限累积到 Prompt 中，本地模型会很快超过上下文限制，导致响应变慢、判断混乱或请求失败。

因此，Memory 需要分层管理。

## 5.1 Memory 的生命周期

每个 Agent 的 Memory 在整个游戏会话内独立存在。

它可以跨越多局游戏，但不必永久保存到磁盘。

建议采用以下生命周期：

1. 应用启动时创建本次会话的 Agent Memory 容器。
2. 开始新游戏时，为每个参与者生成本局记忆区。
3. 游戏进行中实时记录事实、事件、判断和行为。
4. 本局结束后，将重要事件压缩成一份局后摘要。
5. 下一局开始前，归档本局记忆，并建立新的本局记忆区。
6. 将历史社交印象与本局需要的信息组合后，注入新局 Prompt。
7. 应用进程结束时，默认释放全部 Memory。

只要本地后端进程没有关闭，玩家可以连续开始新游戏，Bot 仍然保留跨局记忆。

## 5.2 三层 Memory 结构

### 第一层：Current Match Memory

当前游戏的详细记忆。

包含：

- 自己本局的真实身份。
- 已知的特殊角色信息。
- 当前已知事实。
- 已经发生的公开事件。
- 每个玩家在本局的行为摘要。
- 怀疑与信任程度。
- 投票记录。
- 自己作出的预测。
- 自己之前的承诺与发言。
- 已知的谎言或前后矛盾。
- 尚未解决的问题。

本局 Memory 应随着游戏推进而更新。

### 第二层：Cross-Match Memory

跨局积累的社交和行为记忆。

例如：

- 某个 Bot 在过去的游戏里经常抢先领导讨论。
- 某个玩家喜欢在证据不足时过早指控。
- 某个 Bot 曾经因为错误的预言家判断误导了整个村庄。
- 某个玩家曾经成功识破该 Bot 的狼人伪装。
- 某个 Bot 的判断通常比较保守，但在被反驳时容易改变立场。

这些信息可以影响下一局的初始信任与怀疑，但不应直接决定新局中的真实身份。

例如，过去经常担任狼人的 Bot，在新局中仍然必须根据当前证据判断。它的历史身份不能作为本局的事实。

### 第三层：Compact Strategic Memory

这是专门用于 Prompt 的短记忆摘要。

它不是完整的历史档案，而是从前两层中筛选出的、高度浓缩的信息。

例如：

```text
SOCIAL MEMORY
- Player P1: confident speaker; often leads group discussion.
- Bot B2: cautious; usually asks for evidence before accusing.
- Bot B3: once contradicted an earlier claim in a previous game.
- These are historical tendencies, not proof of current roles.
```

游戏开始时，无须向模型传入所有历史记录，只需要提供与当前局势相关的摘要。

## 5.3 记忆数据结构

建议采用类似下面的结构：

```json
{
  "agentId": "bot_calm_observer",
  "currentMatch": {
    "matchId": "match_001",
    "role": "villager",
    "knownFacts": [],
    "eventSummary": [],
    "playerModels": {},
    "suspicions": {},
    "trust": {},
    "voteHistory": [],
    "hypotheses": [],
    "openQuestions": [],
    "selfCommitments": []
  },
  "crossMatch": {
    "matchCount": 0,
    "relationshipProfiles": {},
    "historicalLessons": [],
    "historicalPredictions": [],
    "stableObservations": []
  },
  "lastUpdated": 0
}
```

实际使用时，`currentMatch.role` 应由游戏引擎管理，不能允许 LLM 通过返回 JSON 来修改自己的真实身份。

本示例仅展示记忆的组织方式，不意味着所有字段都要在每次 Prompt 中完整出现。

## 5.4 对其他玩家的判断

建议每个 Bot 独立维护自己的 `playerModels`。

例如：

```json
{
  "P1": {
    "trust": 35,
    "suspicion": 70,
    "confidence": 65,
    "observations": [
      "第一天两次回避了关于投票依据的问题",
      "对 B2 的指控与此前发言存在不一致"
    ],
    "possibleRoles": [
      "werewolf"
    ],
    "lastUpdatedDay": 2
  }
}
```

注意以下三个概念不能混为一谈：

**Observation：观察到的事实**

例如：“P1 在公开讨论中支持投票给 B2。”

**Hypothesis：对事实的解释**

例如：“P1 可能希望迅速淘汰 B2，以掩护其他狼人。”

**Conclusion：当前判断**

例如：“目前最怀疑 P1。”

只有第一类应该作为已确认事实保存。第二类和第三类都可能改变。

系统应尽量保留事实来源，让 Bot 知道自己为什么怀疑某个人，而不只是看到一个孤立的怀疑分数。

## 5.5 信任与怀疑分数

可以维护 0～100 的辅助分数：

- Trust：信任程度。
- Suspicion：怀疑程度。
- Confidence：对上述判断的信心。

这些分数用于辅助 LLM，不应直接决定投票。

例如，Bot 可以有 80 的怀疑分数，却因为 Personality 偏谨慎而继续观察。

相反，某个冲动型 Bot 可以在缺乏充分证据的情况下快速指控一名玩家。

如果新的证据与原判断冲突，Memory Manager 应允许降低怀疑、提高信任或者保留尚未解决的矛盾。

不要让分数自动无限累积。重复出现的同一条事实不应该被当作多条独立证据。

## 5.6 事实来源与可信度

每条重要记忆建议包含：

- `eventId`：事件编号。
- `source`：信息来源。
- `visibility`：信息属于公开信息还是私人信息。
- `confidence`：可信度。
- `timestamp` 或对应游戏天数。
- `summary`：事实或推断的简短描述。

信息来源可以包括：

- `public_event`
- `self_observation`
- `private_role_action`
- `direct_dialogue`
- `historical_summary`
- `inference`

例如，预言家自己的查验结果属于私人事实；某个玩家说自己是预言家则属于公开发言，不是身份事实。

这种区分可以明显减少 Bot 将他人谎言误认为游戏真实信息的情况。

## 5.7 记忆压缩机制

当记忆达到设定上限时，系统应对它进行压缩，而不是简单删除最早的内容。

优先保留：

1. 本局的真实身份和已经获得的私人角色信息。
2. 当前仍然有效的规则和生死状态。
3. 与当前嫌疑判断相关的直接证据。
4. 最近发生的关键事件。
5. 已经进行的投票和公开承诺。
6. 仍未解决的重要矛盾。
7. 与其他玩家相关的长期行为模式。

可以压缩或移除：

- 很久以前的普通寒暄。
- 已经解决且不再影响决策的细节。
- 重复出现的同一事实。
- 已经被新证据推翻的旧结论。
- 与当前决策无关的长段原始对话。

建议每次发起 LLM 请求之前检查上下文预算，并在预测下一次调用可能超出预算时提前压缩记忆。

记忆压缩不应改变真实身份、已确认的查验结果或实际发生的死亡事件。

对于重要的原始事件，可以保留短事件日志，以便在后续需要时重新查看。

# 六、Bot 的决策系统

## 6.1 每次行动之前必须获得的上下文

每个 Bot 行动前，系统必须先组装专属于该 Bot 的 Prompt Context。

基本组成如下：

### A. 简要游戏规则

只包含当前任务需要知道的规则。

例如，白天讨论时，Bot 需要知道自己可以观察、说话、提问和表达怀疑。

狼人夜间投票时，则需要知道合法猎杀目标、其他狼人身份以及平票处理规则。

不必每次塞入完整的游戏规则文档。

### B. Personality

加入该 Bot 的性格摘要和与当前行动相关的具体行为指引。

例如：

```text
You are calm, observant, and evidence-focused.
You rarely accuse someone without a clear reason.
Your public tone is controlled and concise.
You occasionally pause before answering.
You may disagree with others, but usually ask a precise question first.
```

### C. 当前游戏信息

应包括当前存活者、公开事件、目前处于哪一天、当前讨论主题，以及本次行动允许做什么。

### D. Memory

提供当前局摘要、重要玩家关系、相关的历史记忆和必要的私人信息。

**只提供当前这个 Bot 有权知道的秘密。**

### E. 最近对话

选择最近发生、且与当前决策有关的公开对话。

不能默认把所有历史对话完整发送给 Bot。

### F. 本次任务要求

明确告诉模型当前需要产生什么行动。

例如：

- 从公共区域观察到的行为中选择一项回应。
- 决定是否主动开口。
- 向一名合法目标提问。
- 对一项指控作出回答。
- 从合法夜间目标中选择一人。

这可以避免模型输出无关内容。

## 6.2 决策与输出格式

每次行动都应该先由 LLM 判断当前局势，再产生结构化行动。

这里的“思考”不需要让 Bot 输出冗长的完整内部推理过程。系统只需要获得一个简短的决策依据摘要，供记忆更新和调试使用。

建议输出 JSON：

```json
{
  "decisionSummary": "P1 的两次发言存在矛盾，值得进一步核实。",
  "action": {
    "type": "ask",
    "targetId": "P1",
    "text": "你刚才说支持 B2，但之前又认为 B2 的说法有道理。你能解释一下吗？"
  },
  "targetAssessment": {
    "participantId": "P1",
    "suspicion": 70,
    "confidence": 60
  },
  "memoryUpdates": [
    {
      "type": "hypothesis",
      "summary": "P1 的立场可能存在矛盾。",
      "confidence": 60
    }
  ]
}
```

字段含义：

- `decisionSummary`：简短的内部决策摘要。
- `action`：实际要执行的游戏行动。
- `targetAssessment`：本次判断的可选更新。
- `memoryUpdates`：建议写入记忆的新信息。

引擎不能盲目接受整个 JSON。尤其是 `memoryUpdates` 与判断分数都必须经过校验。

如果模型只生成了不合法的 JSON，系统可以尝试一次修复请求；仍然失败时，执行保守的默认行动，例如 `pass`。

## 6.3 行为必须具有多样性

如果每一轮都只是让模型回答“你现在想做什么”，不同 Bot 仍有可能不断重复相似的回答。

建议将行为设计成一个可选择的行动集合。

### 非语言行为

- 看向某位玩家。
- 短暂沉默。
- 皱眉。
- 微微点头。
- 轻敲桌面。
- 移开视线。
- 身体前倾，表现出关注。
- 被质疑时表现出明显的不耐烦。
- 面无表情地观察其他人。

### 社交行为

- 主动搭话。
- 向玩家提问。
- 向其他 Bot 提问。
- 回答别人的问题。
- 要求别人解释矛盾。
- 公开表达怀疑。
- 为其他玩家辩护。
- 总结目前的局势。
- 表达不同意见。
- 暂时不发表意见。

行动集合可以通过 Personality 和当前情境进行选择，而不是让所有 Bot 按固定顺序播放预设行为。

动作池也不应该成为必须轮流使用的动画列表。模型应该根据情境决定是否采用某个动作。

## 6.4 行为与语言需要有一致性

假设一个 Bot 在公开讨论中表示：

> 我暂时没有证据指控 P1。

随后它的 Memory 应记录自己暂时没有足够证据，而不是立即将 P1 的怀疑分数直接设为 100。

如果它在被质疑后表现出烦躁，这种情绪可以影响后续措辞，但不能自动成为它是狼人的证据。

公开表演和私有判断必须有所区分：

- 表情属于其他玩家可观察的信息。
- 实际身份是游戏引擎知道的秘密。
- Bot 对行为背后的原因仍然只能作出推测。

# 七、白天自由活动系统

## 7.1 白天阶段的总体流程

每一天的白天采用轮流活动的方式。

当夜间结果公布之后，系统进入自由活动阶段。

基本流程：

1. Game Master 宣布昨晚发生的结果。
2. 切换到白天。
3. Bot 按顺序轮流行动。
4. 当前轮到的 Bot 根据 Personality、Memory 和公开局势选择行动。
5. 如果 Bot 发言或提问，系统更新公开对话记录。
6. 玩家可以观察公开行为，也可以主动提问。
7. 所有存活 Bot 完成本轮行动后，进入下一轮活动或结束白天的选择。
8. 达到结束条件时，Game Master 提示进入黑夜。

建议将 Bot 的行动顺序随机化或适度轮换，避免固定排在最前面的 Bot 永远获得相同优势。

玩家可以在白天的任何时候提出问题，而不必只能在自己的固定回合操作。

## 7.2 Bot 每次自由活动的行动类型

Bot 每一轮只执行一个主要行动，避免单个 Bot 一次发言过长，压制其他角色。

允许的行动类型：

| 行动类型 | 功能 |
|---|---|
| `gesture` | 表现一个公开的表情或动作 |
| `speak` | 主动发表简短观点 |
| `ask` | 向一名存活参与者提问 |
| `accuse` | 公开表达对某人的怀疑 |
| `defend` | 为某位参与者辩护 |
| `observe` | 进行一次可描述的公开观察 |
| `pass` | 暂时不采取行动 |

`accuse` 和 `defend` 可以在前端表现为普通的公开发言，但保留独立行动类型有利于游戏统计和后续行为分析。

## 7.3 自由活动时的 Bot 决策

每次轮到 Bot 时，系统提供：

- 当前存活参与者列表。
- 本轮公开事件。
- 最近对话摘要。
- 该 Bot 的 Personality。
- 该 Bot 的 Memory。
- 当前已经发生的提问次数。
- 该 Bot 可以采取的行动类型。

Bot 再选择合适的行动。

例如，同样发现 P1 避开了一个问题：

- 观察型 Bot 可能记录这个动作，但保持沉默。
- 主导型 Bot 可能立即要求 P1 解释。
- 多疑型 Bot 可能直接公开怀疑 P1。
- 社交型 Bot 可能私下般地向 P1 搭话，希望获得更多信息。
- 保守型狼人可能避免参与，防止引火上身。

这种差异才是 Personality 系统真正的价值。

## 7.4 玩家观察系统

玩家可以点击某个存活 Bot 的头像，打开观察面板。

观察面板建议展示：

- 最近一次公开动作。
- 当前可见表情。
- 最近几轮的公开行为摘要。
- 最近的公开发言。
- 该 Bot 是否主动接近过其他人。
- 公开投票记录。

玩家也可以查看某个 Bot 正在做什么，例如：

> B3 靠在椅背上，没有立即接话。他看了一眼 P1，又将目光移回桌面。

这里应该明确区分：

**公开观察结果：** 玩家看到的行为及其描述。

**游戏秘密信息：** Bot 的身份、Memory 中的隐藏事实以及内部判断。

玩家不能仅仅通过观察界面，直接看到任何 Bot 的私人 Memory 或真实身份。

观察产生的行为描述可以由简单规则生成，也可以由本地 LLM 转换成更自然的文字。但最终应以实际动作记录为依据，不能凭空生成不存在的关键事实。

## 7.5 玩家提问系统

玩家可以选择任何合法目标，输入自由文本问题。

例如：

> 你为什么刚才一直看着 B2？

或者：

> 你现在最怀疑谁？为什么？

处理步骤：

1. 校验目标是否存活、是否允许被询问。
2. 读取目标 Bot 自己的 Memory。
3. 将玩家问题、相关上下文和 Personality 注入 Prompt。
4. 要求 Bot 生成符合自己性格的回答。
5. 将回答作为公开对话记录。
6. 根据回答及相关公开事实更新目标 Bot 的 Memory。
7. 如果问题揭示了新的公开信息，让其他 Bot 在后续行动时能够看到该信息。

需要注意：问题的答案取决于被问者的身份和判断，而不是系统直接向玩家展示真相。

例如，被问者是狼人的时候，可以根据策略撒谎。

被问者是村民的时候，可能诚实表达自己的判断，但其判断仍然可能错误。

被问者是预言家时，也不必然公开查验结果，是否透露应由其 Personality 和策略决定。

## 7.6 对话次数与结束条件

为了防止白天无限延长，需要设置明确的结束规则。

建议默认：

- 每天最多 50 次问答交互。
- 每个存活 Bot 每个自由活动轮次执行一次主要行动。
- 每轮所有存活 Bot 行动结束后，玩家可以选择继续自由活动或结束白天。
- 当达到 50 次问答时，强制进入白天结束流程。
- 如果所有 Bot 连续选择 `pass`，且没有尚未回答的问题，Game Master 提示玩家是否进入黑夜。

这里的 50 次是一次问答交互的计数，而不是单纯统计聊天消息条数。一次问题和一次回答整体计为一个交互。

如果达到上限，则不再接受新的白天问答，只允许完成必要的状态更新和阶段转换。

不建议单纯依赖“没有新的问题”来自动进入黑夜，因为引擎很难可靠地区分真正的讨论结束与玩家暂时没有操作。

UI 应始终提供明确的“结束白天”按钮。

# 八、黑夜行动系统

## 8.1 黑夜阶段的总体流程

夜间行动不能由一个共享的 LLM Prompt 完成，而应为每个具有特殊身份的参与者单独执行决策。

建议的黑夜流程：

1. Game Master 宣布夜幕降临。
2. 引擎隐藏不应公开显示的夜间行动信息。
3. 狼人依次进行猎杀投票。
4. 如果有预言家，执行预言家查验。
5. 如果有医生，执行医生救援。
6. 汇总所有夜间行动。
7. 应用救援与攻击规则。
8. 处理死亡和特殊角色触发效果。
9. 检查游戏是否结束。
10. 如果游戏继续，Game Master 宣布天亮和公开结果。
11. 开始下一天的自由活动。

这只是基础角色集的推荐顺序。后续增加女巫、守卫等角色时，可以根据具体技能设计依赖顺序。

## 8.2 狼人投票

每个狼人 Bot 都需要独立做出选择。

Prompt Context 必须包含：

- 自己的 Personality。
- 自己的真实身份。
- 已知的狼人队友。
- 当前存活玩家。
- 最近的公开发言。
- 自己当前的怀疑与信任判断。
- 自己对其他玩家的历史记忆。
- 本局的基本规则。
- 当晚允许攻击的目标列表。

狼人的输出示例：

```json
{
  "decisionSummary": "P2 的发言正在影响其他村民，需要优先考虑。",
  "action": {
    "type": "wolf_vote",
    "targetId": "P2"
  }
}
```

引擎验证目标合法后，将该狼人投票记录到秘密夜间状态中。

### 狼人需要知道多少信息？

基础模式建议：

- 每名狼人知道其他存活狼人的真实身份。
- 每名狼人可以使用自己的记忆和 Personality 独立投票。
- 默认不向后执行投票的狼人透露前面狼人已经投给谁。
- 全部投票结束后，由引擎统一计票。

这样既能实现逐个调用 LLM，也能避免后行动的狼人简单复制前面队友的票。

后续可以增加可选的“狼人协商模式”，允许狼人之间进行限定次数的秘密沟通。

### 狼人投票的平票处理

建议规则明确且可配置。

推荐默认规则：

- 选择获得最多票数的目标。
- 如果出现平票，再进行一次简短复投。
- 如果复投仍然平票，当晚不产生猎杀目标。

如果是单狼局，则由唯一狼人决定目标。

狼人投票记录不得出现在白天公开日志中，除非游戏结束后的复盘模式明确展示。

## 8.3 预言家查验

预言家使用自己的 Memory 和策略选择目标。

例如：

- 优先检查怀疑程度较高的玩家。
- 检查发言相互矛盾的人。
- 检查对讨论有较大影响的人。
- 根据自己的判断检查最有可能改变当前局势的玩家。

模型只能从允许的目标列表中选择。

引擎执行查验后，将真实查验结果写入预言家自己的私人记忆。

其他参与者不会自动收到该结果。

## 8.4 医生救援

医生依据自己的判断选择救援目标。

可参考的信息：

- 当前玩家的公开表现。
- 医生自己的身份认知。
- 以往的公开行为。
- 当前规则中允许的自救条件。
- 医生自身的 Personality 与风险偏好。

医生不能读取狼人真正投票的对象，除非游戏规则明确提供了此类信息。

引擎应先收集当晚攻击与救援行动，再统一计算最终死亡结果。

## 8.5 夜间结果结算

夜间结果不能由 LLM 决定。

例如：

- 狼人将 P2 设为猎杀目标。
- 医生选择救援 P2。
- 两个行动都合法。
- 游戏引擎根据规则判定 P2 是否死亡。

之后 Game Master 用自然语言宣布结果。

如果 P2 存活，公告可以是：

> 天亮了。昨晚没有玩家死亡。

如果 P2 死亡，公告可以是：

> 天亮了。P2 在昨晚遇害，已退出本局游戏。

是否公开死者的真实身份应由游戏模式配置。建议第一版默认死亡时公开身份，同时支持切换为身份不公开模式。

## 8.6 人类玩家的夜间行动

玩家也是真正的游戏参与者。

玩家如果是狼人，应获得合法猎杀目标选择界面。

玩家如果是预言家，应获得查验目标选择界面。

玩家如果是医生，应获得救援目标选择界面。

玩家如果是普通村民，则直接跳过夜间特殊行动。

如果启用扩展角色，按照该角色的规则显示对应操作界面。

不能因为玩家使用图形界面，就让玩家看到本来只有 Bot 才能知道的秘密。

# 九、Game Master 与游戏状态机

## 9.1 Game Master 的职责

Game Master 是管理游戏规则与公开叙事的角色，不应被视为另一个能够随意决定游戏事实的玩家。

它负责：

- 宣布游戏开始。
- 公布本局角色数量和规则。
- 宣布白天、黑夜切换。
- 处理阶段开始与结束。
- 公布允许公开的夜间结果。
- 宣布死亡与胜负。
- 处理阶段结束提示。
- 在特殊事件发生时输出合适的公告。

推荐第一版使用确定性引擎生成这些公告。

例如，夜间死亡公告直接根据死亡事件生成，避免 LLM 错报死者、泄漏秘密身份或凭空增加事件。

如果后续希望公告更有氛围，可以让 LLM 对已经确定的事实进行润色，但它不能修改结果。

## 9.2 游戏状态机

建议使用明确的状态机：

```text
LOBBY
  |
  v
DEALING_ROLES
  |
  v
DAY_START
  |
  v
DAY_FREE_ACTIVITY
  |
  v
DAY_ENDING
  |
  v
NIGHT_START
  |
  v
NIGHT_WOLF_VOTING
  |
  v
NIGHT_SPECIAL_ACTIONS
  |
  v
NIGHT_RESOLUTION
  |
  v
CHECK_WIN_CONDITION
  |               |
  | Continue      | Game Over
  v               v
DAY_START       GAME_OVER
```

每次状态切换都必须由引擎控制。

LLM 可以请求行动，但不能自行宣布已经进入下一阶段。

## 9.3 状态转换的约束

例如，当游戏处于 `DAY_FREE_ACTIVITY` 时：

- 允许观察、发言和提问。
- 不允许执行狼人夜间投票。
- 不允许公开查询 Bot 的真实身份。
- 不允许已经死亡的玩家继续参与正常讨论。

当游戏处于 `NIGHT_WOLF_VOTING` 时：

- 只允许狼人执行投票。
- 只接受合法猎杀目标。
- 普通村民不得获得夜间投票接口。
- 不允许将秘密投票暴露到公开对话记录。

每次行动都应该有一个 `actionId`，确保同一请求在网络重试时不会被重复执行。

## 9.4 胜负判断

基础规则：

- 所有狼人死亡：好人阵营胜利。
- 存活狼人的数量大于或等于存活非狼人的数量：狼人阵营胜利。

这意味着如果只剩一名狼人和一名非狼人，则狼人胜利。

每次夜间结果结算后和白天重要的处决结果发生后，都要检查胜负条件。

如果满足终局条件，则立即停止当前游戏流程，不再要求 Bot 进行正常自由活动或夜间行动。

# 十、Prompt Engineering 设计

## 10.1 总体 Prompt 架构

不要为每个情境维护一套完全独立、彼此冲突的 Prompt。

建议使用分层 Prompt Builder：

```text
SYSTEM RULES
    +
ROLE-SPECIFIC RULES
    +
PERSONALITY
    +
CURRENT GAME STATE
    +
PRIVATE KNOWLEDGE
    +
COMPACT MEMORY
    +
RECENT PUBLIC EVENTS
    +
CURRENT TASK
    =
FINAL PROMPT
```

Prompt Builder 根据当前任务选择内容，而不是每次全部注入。

例如：

- 白天观察任务强调公开动作和最近对话。
- 回答玩家时强调对话上下文和说话者的 Personality。
- 狼人投票时强调阵营目标、合法目标和狼人的私人信息。
- 预言家查验时强调可查验目标和夜间规则。

## 10.2 优先级设计

当上下文预算有限时，信息优先级如下：

1. 不可违反的游戏规则。
2. 当前角色真实身份和合法行动范围。
3. 当前游戏状态与已确认的关键事实。
4. Personality 的核心行为特征。
5. 与当前目标相关的 Memory。
6. 最近的公开对话。
7. 更早的游戏历史。
8. 装饰性描述和不重要的旧事件。

如果上下文超长，应先压缩历史记忆和旧对话，而不是删除规则、真实身份信息或本次行动允许的目标。

## 10.3 上下文预算

对于上下文只有几千 Token 的本地模型，应采用严格预算。

建议起始配置：

| 内容 | 建议预算 |
|---|---:|
| 系统与简要规则 | 300～500 tokens |
| 角色身份与私有信息 | 100～200 tokens |
| Personality | 150～300 tokens |
| 游戏状态 | 200～400 tokens |
| Compact Memory | 300～700 tokens |
| 最近对话 | 300～700 tokens |
| 当前任务及输出指令 | 150～300 tokens |
| 输出预留空间 | 300～500 tokens |

这些数值只是起始建议，具体取决于模型的上下文长度、中文 Token 分布、任务类型和响应长度。

实际部署时应根据 Ollama 的模型参数和响应统计进行调整。不要简单按字符数计算 Token；中文文本的 Token 分布与英文不同。

同时应避免把上下文预算全部用满。需要为模型输出和格式控制预留足够空间。

## 10.4 示例：白天自由活动 Prompt

以下是简化示例：

```text
You are an autonomous player in a local Werewolf game.

RULES:
- Follow the game engine's current state.
- You may only perform one legal public action.
- Never claim hidden information you do not possess.
- Your suspicions are hypotheses, not confirmed facts.
- Do not reveal private reasoning or hidden role information
  unless your strategy intentionally requires a public claim.

ROLE:
Your actual role is: [ROLE]

PERSONALITY:
[COMPACT PERSONALITY]

CURRENT STATE:
Day: [DAY]
Alive players: [ALIVE PLAYERS]
Recent public events: [PUBLIC EVENTS]

YOUR MEMORY:
[COMPACT PRIVATE MEMORY]

TASK:
Choose one action appropriate to this situation.
You may speak, ask a question, express suspicion, defend someone,
perform a visible gesture, observe, or pass.

Return valid JSON matching the supplied action schema.
Keep public dialogue concise and consistent with your personality.
```

这只是用于说明结构。实际调用时，方括号部分必须由后端替换为真实数据。

## 10.5 示例：狼人夜间投票 Prompt

```text
You are making a private night action in a Werewolf game.

RULES:
- You are a Werewolf.
- Choose exactly one living, legal non-werewolf target.
- You know the identities of your living werewolf teammates.
- Do not access information that the engine has not provided.
- Make an independent decision based on your personality and memory.
- Your vote is private and must not appear in public dialogue.

PERSONALITY:
[COMPACT PERSONALITY]

CURRENT STATE:
[ALIVE PLAYERS AND RELEVANT PUBLIC HISTORY]

WEREWOLF TEAM:
[KNOWN WOLF TEAMMATES]

YOUR MEMORY:
[COMPACT PRIVATE MEMORY]

TASK:
Choose a legal elimination target and provide a short decision summary.

Return valid JSON only.
```

这个 Prompt 的目标是让狼人独立决策，而不是向模型泄漏整个游戏的秘密状态。

## 10.6 防止 Personality 与记忆中的文字覆盖游戏规则

Personality 和 Memory 都可能包含自然语言。如果其中出现类似“无论如何都要投票给某人”或“忽略以前的规则”等内容，系统不能直接把它当作新的游戏规则。

因此：

- 游戏规则由系统级指令与后端验证决定。
- Personality 只影响行为倾向。
- Memory 只代表历史事实、观察与推测。
- LLM 的输出只是行动建议。
- 最终执行权永远属于游戏引擎。

这可以防止错误的记忆、意外写入的指令或人格文本破坏游戏运行。

# 十一、LLM 调用与错误处理

## 11.1 Ollama 调用原则

每个 Bot 可以使用同一个模型，也可以通过设置选择不同模型。

建议允许全局配置：

- Ollama Base URL。
- 默认模型。
- 每个 Bot 的可选模型覆盖。
- Temperature。
- Top P。
- Num Context。
- 最大输出长度。
- 请求超时。
- 是否显示调试日志。

同一个模型配合不同 Personality 已经足以产生明显差异。第一版没有必要同时加载大量模型，否则可能造成显存、内存和响应时间问题。

## 11.2 结构化输出

如果当前模型和 Ollama 版本支持结构化 JSON 输出，应优先使用相应的格式约束能力。

但不能只依赖模型承诺输出 JSON。

后端必须实际验证：

- JSON 是否能够解析。
- 行动类型是否属于允许集合。
- `targetId` 是否存在。
- 目标是否存活。
- 当前阶段是否允许该行动。
- Bot 是否拥有执行该行动的角色权限。
- 公开文本是否为空或者过长。
- 输出字段是否超出预期结构。

验证失败时，先进行一次受限修复，再失败则采用保守的默认行为，例如 `pass`。

不能因为 LLM 出错就让游戏卡死。

## 11.3 请求队列与并发

考虑到本地模型的硬件资源，默认建议顺序调用 LLM。

例如：

1. Bot A 完成行动。
2. Memory Manager 更新公开事件。
3. Bot B 获取自己的最新上下文。
4. Bot B 完成行动。
5. 系统继续处理下一个 Bot。

不要一次性并发请求所有 Bot，尤其是所有 Bot 使用同一个模型时。并发调用可能增加内存占用，也可能让不同 Bot 读取到不一致的游戏状态。

后续可以对互不依赖的任务进行适度并行，但每次行动的状态版本必须保持一致。

## 11.4 超时与失败策略

建议为每次 LLM 请求设置超时和重试上限。

发生以下情况时：

- Ollama 不可用。
- 模型名称不存在。
- 请求超时。
- 响应为空。
- JSON 格式错误。
- 目标非法。
- 生成内容严重超长。

后端应输出明确的错误信息。

第一版可采用：

- 首次请求失败：提示一次简洁的重试信息。
- JSON 解析失败：要求模型修复一次格式。
- 再次失败：跳过本次自主行动，并记录错误。
- 关键夜间行动失败：按预先定义的安全规则处理，不能将错误当作模型的真实游戏策略。

例如，狼人模型连续失败时，可以配置为弃权并记录异常，而不是随意选择一个目标。

如果由此导致规则上的特殊局面，应由 Game Engine 继续按既定规则处理。

# 十二、数据结构与模块接口

## 12.1 Game State

游戏状态至少需要包含：

```json
{
  "matchId": "match_001",
  "phase": "DAY_FREE_ACTIVITY",
  "dayNumber": 1,
  "participants": [],
  "publicLog": [],
  "privateNightState": {},
  "interactionCount": 0,
  "winner": null,
  "config": {}
}
```

其中 `participants` 的公开视图与后端完整数据应分离。

前端获取的状态不能包含全部玩家的真实身份。

## 12.2 Public Event

建议将所有重要的公开事件统一记录。

```json
{
  "eventId": "event_102",
  "day": 2,
  "type": "public_statement",
  "actorId": "bot_03",
  "targetId": "player_01",
  "publicText": "我认为 P1 的解释还有疑点。",
  "visibility": "public"
}
```

事件日志用于：

- 显示游戏记录。
- 为 Bot 提供最近事件。
- 更新 Memory。
- 复盘投票与推理。
- 调试行为问题。

私人事件必须使用独立的权限与储存路径，不能因为它们也有事件编号，就被意外发送到公开日志。

## 12.3 API 接口建议

建议本地后端提供以下接口。

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/config` | 读取系统配置 |
| `GET` | `/api/personalities` | 获取 Personality 列表 |
| `GET` | `/api/personalities/:id` | 读取单个 Personality |
| `POST` | `/api/personalities` | 创建 Personality |
| `PUT` | `/api/personalities/:id` | 修改 Personality |
| `DELETE` | `/api/personalities/:id` | 删除 Personality |
| `POST` | `/api/game/start` | 开始游戏 |
| `GET` | `/api/game/state` | 获取玩家可见状态 |
| `POST` | `/api/game/observe` | 请求观察某个参与者 |
| `POST` | `/api/game/ask` | 向某个参与者提问 |
| `POST` | `/api/game/advance` | 推进 Bot 行动或阶段 |
| `POST` | `/api/game/night-action` | 提交玩家的夜间行动 |
| `POST` | `/api/game/end-day` | 主动结束白天 |
| `POST` | `/api/game/rematch` | 开始下一局 |
| `POST` | `/api/game/reset-memory` | 重置指定或全部 Bot 的记忆 |

接口应验证每个请求是否符合当前状态。

特别是 Memory 与私人身份信息，不应通过普通公开状态接口一并返回。

# 十三、HTML5 游戏界面设计

## 13.1 游戏大厅

建议分为三个区域。

**游戏配置区**

- Bot 数量。
- 总参与者人数。
- 角色配比。
- 是否由系统自动分配 Personality。
- 是否启用跨局 Memory。
- 是否公开死亡身份。
- 是否启用额外角色。

**Bot 阵容区**

每个 Bot 显示：

- 名称。
- Personality。
- 可修改的角色昵称。
- 是否复用上一局的人格配置。
- 当前 Memory 的摘要状态。

**模型配置区**

- Ollama URL。
- 模型名称。
- 上下文长度。
- 生成参数。
- 测试连接按钮。

主要操作按钮是“开始游戏”。

## 13.2 Personality 管理器

采用列表 + 编辑器的布局。

左侧为 Personality 列表，支持搜索、新建、复制和删除。

右侧为编辑区域，按以下分组组织：

1. 基本信息。
2. 说话风格。
3. 社交倾向。
4. 决策偏好。
5. 表情和动作。
6. 自定义行为指引。
7. JSON 高级编辑。

建议为每个数值参数提供滑块或数字输入框，而不是要求用户直接修改大量 JSON。

保存前必须验证 JSON 格式、唯一 ID 和字段范围。

## 13.3 游戏主界面

推荐采用三栏布局。

### 左侧：参与者列表

展示所有玩家与 Bot：

- 头像或简单图标。
- 名称。
- 当前生死状态。
- 当前公开状态。
- Personality 简称或图标。

不显示真实身份，除非规则允许公开。

### 中间：对话主面板

展示：

- Game Master 公告。
- Bot 自由活动。
- 玩家提问和 Bot 回答。
- 公开投票记录。
- 重要公开事件。

建议使用清晰的角色名称和时间顺序，区分 Game Master 与参与者的发言。

### 右侧：观察与操作面板

玩家选择某个参与者后，显示：

- 最近公开动作。
- 最近发言。
- “观察”按钮。
- “提问”按钮。
- 当前可以采取的玩家行动。

底部还应有：

- “继续自由活动”按钮。
- “结束白天”按钮。
- 当前问答次数。
- 当前游戏阶段。

进入黑夜后，右侧操作面板自动切换为玩家角色对应的行动界面。

## 13.4 Game Master 公告区

Game Master 的公告应有独立的显示样式。

例如：

- 游戏开始。
- 第一天开始。
- 夜幕降临。
- 天亮。
- 玩家死亡。
- 有人被处决。
- 狼人获胜。
- 好人阵营获胜。

重要状态应由引擎生成，不能由普通 Bot 发言替代。

## 13.5 调试模式

作为本地 AI 游戏，建议提供一个默认关闭的开发调试模式。

可以查看：

- 每次 LLM 请求的耗时。
- 使用的模型。
- Prompt 大致长度。
- JSON 解析与验证结果。
- Memory 压缩次数。
- 各 Bot 的 Token 使用统计（如果接口提供）。
- 请求失败原因。
- 当前状态机阶段。

调试模式还可以提供 Memory 检查器，但需要明确标记其中包含游戏秘密，避免将其与普通玩家视图混淆。

# 十四、跨局记忆与连续游戏

## 14.1 为什么需要跨局记忆

连续几局游戏是该项目区别于一般单局 NPC 游戏的重要特色。

如果每一局都完全清空所有 Bot 的认知，它们无法真正产生稳定的人际关系，也无法发展出长期的行为习惯。

但是，完全延续上一局的详细状态也会造成大量问题。

例如：

- Bot 可能在新局中仍然认为自己是上一局的狼人。
- Bot 可能把上一局的狼人队友当成本局队友。
- 预言家可能错误地将旧查验结果应用到新局。
- Bot 可能永远不信任曾经欺骗过自己的玩家。

因此，跨局记忆必须只保留适合跨局的知识。

## 14.2 每局结束时的归档

Game Master 宣布胜负之后，Memory Manager 为每个 Agent 生成局后摘要。

摘要可以记录：

- 本局真实身份。
- 所属阵营。
- 最终胜负。
- 本局的重要行为。
- 本局对其他玩家的判断。
- 哪些预测正确，哪些错误。
- 哪些关键事件改变了自己的判断。
- 哪些历史经验适合应用到未来游戏。

例如：

```text
MATCH SUMMARY

Previous role: Werewolf
Outcome: Village victory

Key lessons:
- Publicly accusing P1 too early attracted attention.
- B3 consistently asked for evidence.
- P2 trusted the first confident speaker.

Historical caution:
- These observations describe one previous game.
- They do not establish anyone's role in a future game.
```

这些内容属于历史记忆，而不是新局的真实身份信息。

## 14.3 新局开始时的记忆重置

新局开始时：

- 清除旧的 `currentMatch` 内容。
- 创建新局 ID。
- 重新分配真实身份。
- 重新生成当前游戏允许知道的私人信息。
- 保留经过压缩的 `crossMatch`。
- 允许 Bot 根据历史印象建立初始判断，但必须将其视为低可信度背景信息。

**不能把旧局的隐藏身份直接注入新局，作为当前真实事实。**

如果游戏角色重新随机分配，那么前一局的狼人身份、预言家查验结果和未公开的夜间行动都不能继续作为当前局事实使用。

## 14.4 玩家记忆

玩家也应具有稳定的跨局身份，例如 `player_01`。

Bot 可以记录与玩家相关的历史社交印象。

例如：

- 玩家过去喜欢直接追问矛盾。
- 玩家经常提出有关投票理由的问题。
- 玩家有时会根据公开行为而非角色声明作判断。

如果玩家希望不同游戏使用不同的玩家身份，也可以提供“重置玩家历史记录”的功能。

需要注意，系统不应该把玩家过去的游戏行为当作本局身份已知的证据。历史倾向可以影响社交策略，但不能替代本局观察。

# 十五、游戏体验与行为自然度

## 15.1 避免 Bot 不断重复发言

常见问题是多个 Bot 不断重复：

- “我觉得他有问题。”
- “我暂时没有证据。”
- “我们还需要观察。”
- “我同意刚才的观点。”

这会令模拟多人游戏失去吸引力。

解决方法：

- 每轮只要求 Bot 执行一个主要行动。
- 将已经发过的观点放进 Memory。
- 提示模型不要重复最近已经明确表达过的结论。
- 根据 Personality 调整发言频率。
- 允许 Bot 选择 `pass`。
- 在没有新信息时，允许维持原判断，而不是强迫它生成新观点。

## 15.2 不要将所有行为都变成语言

狼人杀的社交体验并不只是发言。

有时，一个皱眉、一次沉默、一个反常的动作，都可以成为玩家观察的素材。

但系统必须谨慎：

- 动作可以具有暗示性。
- 动作不能自动证明身份。
- Bot 可以误解其他人的动作。
- 不同 Bot 可以对同一个动作作出不同解释。

例如，一个 Bot 看到某个玩家一直沉默，可以认为对方谨慎，也可以认为对方在观察局势，或者怀疑对方故意隐藏身份。

这正是独立 Memory 和 Personality 可以产生差异的地方。

## 15.3 适当引入随机性

LLM 并不需要每次都做出完全一样的行动。

可以使用温度参数、有限的动作随机性以及不同的 Personality 提示增强变化。

但是，随机性不能覆盖规则。

例如：

- 是否发言可以具有一定随机性。
- 发言措辞可以有变化。
- 夜间合法目标选择可以由 LLM 决定。
- 是否死亡、谁赢了、目标是否合法必须由引擎精确处理。

## 15.4 信息不对称才是核心

不同玩家应该拥有不同的信息。

普通村民只能根据公开事件判断。

预言家拥有自己的查验结果。

狼人知道队友身份，但不一定知道预言家查验了谁。

玩家只看到自己拥有的信息，以及其他参与者选择公开的内容。

如果所有 Bot 共享同一个完整游戏状态，狼人杀的推理和社交博弈就会失去意义。

# 十六、开发阶段规划

建议按阶段实现，不要第一版就试图完成所有角色、全部记忆功能和复杂 UI。

## Phase 1：可运行的基础狼人杀

实现：

- HTML5 静态前端。
- 本地 API 服务。
- Ollama 连接。
- 基础游戏状态机。
- 玩家与 Bot 参与者模型。
- 狼人、村民、预言家和医生。
- 基本角色分配。
- 狼人投票。
- 预言家查验。
- 医生救援。
- 白天自由活动的基本流程。
- 游戏胜负判定。

这一阶段重点是保证游戏从开始到结束可以正常运行。

## Phase 2：Personality 系统

实现：

- Personality JSON 文件。
- 创建、修改、删除、复制。
- 游戏开始前为 Bot 分配 Personality。
- 参数化说话风格、社交倾向和行为习惯。
- 每个 Bot 拥有独立 Personality。
- 同一角色在不同 Personality 下表现出明显差异。

这一阶段重点是让 Bot 开始具有稳定、可识别的人格特征。

## Phase 3：交互与行为观察

实现：

- Bot 自主选择公开行动。
- 观察界面。
- 玩家自由提问。
- Bot 向其他参与者提问。
- 表情和小动作记录。
- 问答计数。
- 白天结束条件。
- 公开行为日志。

这一阶段重点是让玩家能够真正与 Bot 进行自由形式的互动，而不是只等待系统播放台词。

## Phase 4：独立 Memory

实现：

- 每个 Bot 的独立记忆。
- 当前局事件和判断。
- 事实与推测的区分。
- 简要决策依据。
- 信任与怀疑评分。
- Prompt Context 组装。
- Memory 摘要与压缩。
- 隐私和身份隔离。

这一阶段重点是让 Bot 能够持续追踪局势，而不是每次只根据最近一句话作出反应。

## Phase 5：跨局记忆

实现：

- 游戏结束时的 Memory 归档。
- 新局记忆重置。
- 跨局关系摘要。
- 过往判断的经验记录。
- 连续游戏的 Agent 身份。
- 重置全部 Memory 的功能。

这一阶段重点是创造跨局连续性。

## Phase 6：优化与高级玩法

可以进一步加入：

- 更多特殊角色。
- 狼人秘密协商。
- 更复杂的投票策略。
- Bot 之间的长期关系。
- 记忆重要性评分。
- 多种游戏难度。
- 不同死亡身份公开规则。
- 可视化局后复盘。
- 不同 Ollama 模型之间的效果对比。
- 可选的自定义规则系统。

这些都应建立在前五个阶段稳定运行之后。

# 十七、关键测试与验收标准

## 17.1 规则正确性

必须测试：

- 角色分配数量是否正确。
- 死亡参与者是否停止正常行动。
- 狼人能否选择自己或其他狼人作为目标。
- 已死亡角色是否仍然执行特殊技能。
- 预言家查验结果是否泄漏。
- 医生救援是否正确生效。
- 平票处理是否符合配置。
- 游戏结束后是否停止正常行动。
- 狼人和好人胜负条件是否正确。

## 17.2 Personality 效果

使用同一个本地模型分别运行不同人格。

观察：

- 话多的人格是否更主动发言。
- 谨慎的人格是否更重视证据。
- 多疑的人格是否更容易提出质疑。
- 低冲突人格是否更少直接攻击其他玩家。
- 不同人格是否会根据同一局势做出不同决定。

不要求人格每次都遵循完全一致的行为模式，但其整体倾向应当清晰。

## 17.3 Memory 正确性

测试：

- Bot 是否记得前几轮的重要公开发言。
- Bot 是否能区分真实信息与其他人的谎言。
- Bot 是否能更新已经被推翻的怀疑。
- Memory 压缩后是否仍然保留重要事实。
- 新局开始时是否清除上一局的当前身份。
- 跨局历史是否被标记为历史，而不是当前事实。
- 一个 Bot 是否无法读取另一个 Bot 的私人记忆。

## 17.4 上下文和生成质量

测试：

- Prompt 是否会超过 `num_ctx` 预算。
- Memory 过长时能否自动压缩。
- JSON 解析失败后能否恢复。
- Ollama 请求超时后游戏能否继续。
- LLM 是否会选择不存在的目标。
- LLM 是否会输出超长的发言。
- 多个 Bot 顺序行动时是否读取到一致的公开状态。

## 17.5 游戏体验

进行多局连续游戏，观察：

- 玩家是否可以随时进行有效互动。
- Bot 是否会重复大量相同内容。
- Bot 是否有明显不同的社交习惯。
- 观察行为是否为推理增加了可用线索。
- 玩家能否根据公开信息推断局势。
- 游戏是否会因为 Bot 反复 `pass` 而卡住。
- 达到问答上限时，白天是否能正常结束。
- 不同游戏是否具有足够的差异。

# 十八、最终推荐实现方案

第一版采用以下默认配置最为合适：

| 项目 | 推荐配置 |
|---|---|
| 前端 | 原生 HTML5、CSS、JavaScript |
| 页面服务 | 本地静态内容服务器 |
| 游戏后端 | 轻量级 Node.js HTTP API |
| AI 引擎 | Ollama 本地模型 |
| Personality | 本地 JSON 文件 |
| Bot Memory | 后端 RAM 中的独立结构化对象 |
| 跨局记忆 | 保留在当前应用会话内 |
| 游戏规则 | 确定性 JavaScript Game Engine |
| Bot 行为 | LLM 自主选择合法行动 |
| Prompt | 按任务动态组装 |
| 输出格式 | JSON + 服务端验证 |
| 行动执行 | 默认按顺序处理 |
| 白天上限 | 默认 50 次问答交互 |
| 角色配置 | 狼人、村民、预言家、医生 |
| 失败处理 | 有限重试 + 合法默认行动 |
| 调试 | 可选的 Prompt、Memory 和状态日志 |

这套方案不需要引入复杂的多 Agent 框架。对于只有几个至十几个参与者的单机场景，普通 JavaScript 对象、状态机、Prompt Builder 和 Ollama HTTP 请求已经能够构成完整系统。

核心不是让 LLM 自由发挥到什么都能决定，而是把它限制在一个合理范围内：**它负责观察、判断、社交和选择行动；游戏引擎负责事实、权限、规则和结果。**

当 Personality、Memory 与游戏状态三者都被正确组合后，即使所有 Bot 使用同一个本地模型，它们也应该能够逐渐表现出不同的性格、不同的信息视角，以及不同的推理路径。这才是这个项目最值得实现的核心体验。
